# Field-Agnostic Mavros

The current state of mavros is tied to BN254, but the project should, in general, be agnostic to the
field it is operating over (see #120). This is a multi-stage process that will occur as follows:

- [x] **Phase 1:** Identify all locations where we make assumptions about fields that are not
      field-agnostic.
- [x] **Phase 2:** Add a façade over the existing BN254 using a field abstraction. This should
      produce byte-identical output as it is just an interface change.
- [x] **Phase 3:** Add a `FieldConfig` to the SSA, route the four evaluators, unify `two_pow` and
      kill the modulus/width literals.
- [x] **Phase 4:** Give every supported field a **duplicated set of opcodes** — `add_field` becomes
      `bn254_add_field` (and later `goldilocks_add_field`, …), generated by opcode-gen. A single VM
      binary carries the handlers for every field, and the bytecode's opcodes name its field. This
      ensures that there is no runtime field selection in dispatch, and that the VM can nevertheless
      work with any supported field. The first field's (bn254's) copy of each operation takes the
      operation's position and operand encoding, and only further fields grow the opcode space.
      Codegen emits the field-prefixed opcode chosen from the SSA's `FieldConfig`. The program
      header also names the field (P5), so the VM refuses to run a program over another field.
- [ ] **Phase 5:** Add support for goldilocks through the SSA and the VM using the field
      abstraction. The compiler's `FieldElement` is an enum over the fields' backings (`Bn254(Fr)`
      on arkworks, `Goldilocks` hand-written over `u64`), chosen once per compilation by the
      program's `FieldConfig`; a backing that answers the field at run time (`crypto-primitives`) is
      a later, benchmarked swap. This must support true field width, and not rely on stuffing
      goldilocks into larger limb counts. Two small-field-specific workstreams surface here:
      multi-limb **integer-arithmetic lowering** (Layer 6 — `u64`/`u128` overflow the field and need
      schoolbook limbs + a multi-cell representation) and **repeated LogUp** (`L4-logup-challenges`
      — one challenge is unsound on a small field). The user-facing `--logup-soundness=<bits>` flag
      (default 128) sizes the repetitions the argument needs (one on bn254), and R1CS generation,
      witgen, AD and the forward verifier repeat it that many times; the LLVM and WASM paths refuse
      more than one.

**Phase 3 Complete:** a `FieldConfig` is homed on the `SSA` (`ssa/mod.rs`) and reached through
`ssa.field()` / `b.field()` / the `HLEmitter::field()` trait method; the middle-end's three symbolic
evaluators (click_cooper's lattice, the specializer, the instrumenter) plus the value-range interval
algebra and the PRE totality oracle route their field values through it; the six `two_pow` copies
are down to one; and no site in `compiler/src` names a static `Field::` associated item, a literal
prime, or a literal field width. `Type::get_bit_size(field)` takes the config, so the width of a
`Field` is whatever the configured field's modulus needs.

Two pieces of what the middle-end will eventually need are deliberately **carried into later
phases**, not left undone here:

- The **fourth evaluator**, `codegen/hlssa_to_r1cs.rs`, which P4 moved onto `FieldElement` (see the
  Phase 4 note).
- The `--field` selector that will seed `SSA::field` from the `Driver` (P5). `SSA::empty` seeds
  `FieldConfig::bn254()`, which is why P3 and P4's field generalisation leave bn254's artifacts
  byte-identical.

**Phase 4 Complete:** every field opcode is generated per field. `#[interpreter(fields(..))]` in
`vm/src/bytecode.rs` names the fields (bn254 and the one-cell `Goldilocks` of
`mavros-artifacts/src/field/goldilocks.rs`), opcode-gen emits one `bn254_*`/`goldilocks_*` copy of
each field opcode, and `opcode_numbers_are_pinned` pins every number. Codegen names an operation as
a `FieldOpCode` and picks its copy with `FieldOpCode::for_field(field.id())`, an exhaustive match.
Underneath:

- **`MavrosField`** (`mavros-artifacts/src/field/mavros_field.rs`) is implemented directly on
  `ark_bn254::Fr` and on `Goldilocks`, and carries what the VM needs: `STORAGE_CELLS`,
  `CANONICAL_LIMBS`, frame-cell reads and writes (`from_frame_cells`/`to_frame_cells`,
  `storage_cell0`), canonical limbs and `inverse`.
- **The VM** is generic over `F: MavrosField`: handlers, tapes, AD nodes, batch inversion and the
  `run_*::<F>` entry points. Field-independent opcodes that back-propagate AD (`dec_rc`,
  `array_set`, global drops) learn `F` from the run's `FieldVmOps` table. `wasm_host` reuses the
  generic phase 2.
- **Codegen** sizes every field slot from `FieldConfig::storage_cells()`
  (`codegen/bytecode/layout.rs::slot_cells`), and `hlssa_to_r1cs` computes on `FieldElement`,
  converting to the raw `LC` coefficients with `.to_ark()` where a constant meets one.
- **The WASM path** carries the field into LLSSA (`LLSSA::with_field(hlssa.field())`), names the
  runtime's entry points through `FieldRuntimeSymbols::of(field)`, and the runtime expands
  `field_runtime!` once per field (bn254 keeps its `__field_*` names).

The generalisation leaves bn254's R1CS, bytecode, witnesses and WASM module code byte-identical; the
renumbering below moves the bytecode and its debug sidecar. The WASM module bytes differ only
through the runtime archive, where `field_runtime!` relocates three of the runtime's panic locations
(WASM Size unchanged).

Carried into P5: the WASM struct width (`L3-llstruct`) and the `[4 x i64]` runtime ABI, the
`BigInt<4>`/`[u64; 4]` signatures (`L3-felt-limbs`), the raw `Field` alias (`L1-alias`) and its
serde (`L1-serde`), a second field's runtime instance, `wasm-runner` and the `--field` selector.

**Opcode renumbering:** P4 ends by dropping the opcodes the compiler never emits (`reserved_92`,
`assert_r1c`, `unbox_field`, `tuple_alloc`, `tuple_proj`) and the always-empty struct-layout table
with its `DataType::Struct`, and numbering the remaining opcodes and `DataType`s densely. The
program binary opens with `PROGRAM_MAGIC` and `PROGRAM_FORMAT_VERSION` (`vm/src/bytecode.rs`), and
`parse_program_header` refuses a binary of any other format, whose opcode numbers would select the
wrong handlers. Only the bytecode and its debug sidecar move; R1CS, witnesses and WASM are
byte-identical.

**Phase 5a (Goldilocks on the VM):** a program over Goldilocks compiles to a Goldilocks R1CS and
bytecode and runs on the VM, witgen and AD both checked against the R1CS. Underneath:

- **`Goldilocks`** (`mavros-artifacts/src/field/goldilocks.rs`) is hand-written over `u64`, stored
  in Montgomery form with `R = 2^64`, so a cell is bit-for-bit arkworks' `Fp64` cell (arkworks'
  `Fp64` is its test oracle). A second field instantiated through arkworks' generics shares their
  limb-generic helpers with bn254's, and the VM's `opt-level = "z"` build then outlines them from
  bn254's handlers (+2–14% instructions on bn254 programs); the hand-written field shares none.
- **`FieldElement`** is the enum above. Its `Hash` hashes the value alone, so a bn254 element hashes
  as its `Fr`; arithmetic, `==` and ordering on two fields' elements panic. The middle-end mints its
  constants through `FieldConfig` (`constant` takes `IntoFieldElement`), which refuses an element of
  another field.
- **The VM** carries `goldilocks_*` copies of every field opcode in every build. A program binary
  names its field in its header, and a run over another field is refused.
- **The R1CS** is generic (`R1CS<F>`, with bn254 as the default): `Driver::generate_r1cs::<F>`
  refuses an `F` other than the program's field, `R1CGen<F>` converts constants with
  `MavrosField::from_element`, and a serialized coefficient is `F::CANONICAL_LIMBS` limbs.
- **The artifact** (`program.mavros`: a `MAVR1CS` header with the format version, compiler version,
  field tag and digest) names the field and the format of the system it carries.
- **The WASM path** refuses Goldilocks (`Error::WasmFieldUnsupported`): the runtime has no
  Goldilocks instance.
- **The Noir path** compiles over bn254 only; a Noir `Field` literal enters a configured field only
  below its modulus (`L1-noir-frontend`).
- **LogUp:** at the default `--logup-soundness=128`, a Goldilocks program with a lookup argument
  repeats the argument three times (four for `2^20 < D ≤ 2^31`; `L4-logup-challenges`).

Goldilocks is tested through hand-built SSA (`compiler/tests/bigints/goldilocks.rs`): field
arithmetic, equality and constant folding at the field's boundary values, a witnessed 64-bit
decomposition, and the integer operations of Phase 5b. Two gaps refuse through the `unsupported`
funnel: a witnessed `Field` bit window (`x as uN`), whose canonical decomposition is bn254's, and an
integer entry parameter wider than 63 bits, since an `Int` entry parameter is one entry-blob
element.

**Phase 5b (integer arithmetic on Goldilocks):** the witness limb is the widest power of two `h`
whose limb product is an injective integer, `2h <= widest_injective_int_bits`
(`shared/limbs.rs::limb_bits_for_modulus`): 64 bits on bn254, where the host word caps it, and 16 on
Goldilocks. A limb times a limb or a place value then has one reading as an element, and a
schoolbook column has `2^31` partial products of headroom on Goldilocks, so the schoolbook, the
division and the limb-wise shift take every width. Below them, the single-cell product, division and
right shift are bounded against the modulus, so they hold every `u32` and `i32`.

The suite checks every integer operation against the integer model on Goldilocks either side of each
lowering switch up to 63 bits, and the limbed operations at 63, 64, 100 and 128 bits (256 in an
ignored test) with a witnessed or a constant right operand and with a pure left one, building the
wide operands inside the program from constants selected by witnessed bits. The column-pinning
probes run on each lowering, and `wide_witness_ints`' structural audits run on both fields: a
missing range check on a carry or an answer limb is exploited by moving value between limbs through
a carry, which neither column probe reaches.

**Repeated LogUp** (`L4-logup-challenges`): the driver sizes the argument's repetitions `K` for the
`--logup-soundness` target before sealing and repeats the argument at independent challenges over
shared multiplicities, so the pre-commitment witness is unchanged. bn254 keeps `K = 1`, with
byte-identical constraints and witnesses; the artifact's witness layout and the VM header both carry
`K`. The layout is under `L4-logup-challenges` below.

The rest of Phase 5 is open:

- **A witnessed `Field`'s bit window** (`L3-felt-limbs`): a decomposition against the configured
  modulus in `bit_range.rs::lower_witness_field_bit_range`.
- **Integer entry parameters wider than 63 bits** (`prepare_entry_point.rs`): parameters assembled
  from ABI limbs.
- **The Noir path** (`L1-noir-frontend`): the `--field` selector, and Noir's compile-time bn254
  builtins.
- **Cast semantics** (`analysis/types.rs::check_casts_into_field`, which is to be removed): the
  frontend refuses a non-injective `Int → Field` cast, and HLSSA defines `Int → Field` as reduction
  modulo `p` and `Field → Int` as truncation or zero-extension of the canonical value. Every
  evaluator (the VM, `hlssa_to_r1cs`, the symbolic evaluators, WASM and `WideWitnessInts`' limb
  casts) must implement exactly these semantics, and the witness lowering of a reducing cast of a
  wide witnessed integer needs dedicated constraints. This subsumes the bare
  `cast WitnessOf(Field) -> Int(n)` item under `L1-noir-frontend`.
- **A Goldilocks WASM runtime** (`L3-llstruct`, the `[4 x i64]` runtime ABI, `field_runtime!`), with
  repeated LogUp: a Goldilocks lookup argument needs `K = 3` or 4, and the LLVM and WASM paths
  refuse `K > 1` (`Error::WasmLogupRepetitionsUnsupported`) because the LLSSA AD emitters
  (`hlssa_to_llssa.rs`) bind one repetition's challenges. Emitting them at the `LogupStrides`
  offsets the VM uses lifts the refusal. WASM witgen's phase 2 runs through the interpreter's
  `run_phase2`, which fills every repetition from the phase-1 metadata in repetition 0's rows.
  `repeated_lookup_arguments` in `compiler/tests/verifier.rs` then runs on both backends.
- **`crypto-primitives`** (Layer 5).

The current state has each site of a field assumption tagged with `// FIELD-ASSUMPTION: <tag>`
directly in code. The `<tag>` values match the section headings below.

By convention, definitions and structurally distinct algorithm sites get their own marker.
Repetitive clusters of the same operation get one marker per file with a count.

## How to Read the Checklist

- **`[ ]` / `[x]`** — migration status.
- **Phase** — which roadmap phase touches it (P2 = façade/direct-refs, P3 = `FieldConfig` on SSA, P4
  = per-field opcodes and a field-generic VM, codegen and WASM path, P5 = goldilocks + per-field
  width).
- **Kind** — `type-parametric` (already abstracts over the field via `Field`/`PrimeField`; follows
  the alias automatically once it's generic) vs `hardcoded` (names bn254 / a literal / a fixed width
  and must be rewritten) vs `representation` (assumes the 4-limb/32-byte physical layout) vs
  `algorithmic` (the _lowering strategy_ itself only works with the field's headroom and needs a
  different algorithm on a small field — Layer 6).

Completion gate (Phase 5):
`rg -t rust 'ark_bn254|into_bigint\(|\.0\.0|FELT_LIMBS|FIELD_SIZE|\b254\b'` over
`compiler/ vm/ mavros-artifacts/ opcode-gen/ wasm-runtime/` returns only façade-internal hits. The
gate is open: the search returns 158 lines, 43 of them in `compiler/tests/`.

## Layer 1 — Type Alias & Direct Field References

### `L1-alias` — Single Type Alias (Hardcoded, P2 / raw alias P5)

- [x] `compiler/src/compiler/mod.rs` — the **compiler middle-end's** alias is now
      `pub use mavros_artifacts::FieldElement as Field`. Everything from HLSSA constants through the
      passes and analyses rides it.
- [ ] `mavros-artifacts/src/lib.rs` — `pub type Field = ark_bn254::Fr;` names bn254 for the callers
      that name no field (the Noir path, WASM, the test runner). `LC`/`R1C`/`R1CS`/
      `InputValueOrdered` are generic over `F: MavrosField` with `Field` as the default (P5), so the
      alias is their bn254 instance. `vm/src/lib.rs` re-exports it. `hlssa_to_r1cs`'s `R1CGen<F>`
      computes its `LC`s in `F` and converts a constant at the boundary with
      `MavrosField::from_element`; `Driver::generate_r1cs::<F>` refuses an `F` other than the
      program's field (`Error::R1csFieldMismatch`), and `r1cs_compact::analyze` takes any `R1CS<F>`.

**`FieldConfig` answers per field through exhaustive matches.** Every accessor on
`mavros-artifacts/src/field/config.rs` that depends on the field is an **exhaustive
`match self.id`** or delegates to one (`two_pow` and `constant` to `IntoFieldElement`'s integer
embedding, `modulus_limbs` to `modulus`), so adding a variant to `FieldId` is a compile error at
every such site, where a debug-only assertion would fire only if something constructed the new
config. `FieldConfig` also has **no `Default` impl**, so a config cannot be conjured without naming
a field: between the two, a config can only be constructed deliberately and can only be read through
a match a new field breaks. P5 gives each accessor its Goldilocks arm (`FieldConfig::goldilocks()`).
`modulus() -> BigInt<4>` and `modulus_limbs() -> [u64; 4]` carry a canonical integer zero-extended
to four limbs, and `from_bigint` refuses a Goldilocks integer with a non-zero upper limb, so the
four-limb signatures describe the canonical integer, never a field's storage width
(`L3-felt-limbs`).

### `L1-noir-frontend` — The Noir Frontend Computes in bn254 (Hardcoded upstream, P5)

Noir's `acir_field` chooses bn254 or bls12_381 when Noir is built, so anything Noir evaluates at
compile time wraps modulo bn254's prime. A `Field` literal crosses the boundary unreduced, as the
signed integer written.

- [x] `compiler/src/compiler/lowering/expression_converter.rs` — `integer_constant` takes a
      literal's magnitude into the configured field, refusing one at or above its modulus with a
      located diagnostic, and negates it for a negative literal (so `-1` is `p - 1` on Goldilocks).
- [ ] `compiler/src/driver.rs` — a Noir package compiles over bn254: the driver has no field
      selector, and `--field` waits on the items below.
- [ ] Noir's stdlib (`noir_stdlib/src/compat.nr` `is_bn254()`, `field/mod.nr` `modulus_num_bits()`
      and the `modulus_*_bits`/`_bytes` builtins) answers bn254 at compile time under any configured
      field, so `Field::lt` takes `bn254_lt`, whose decomposition is against bn254's modulus, and
      the canonicity checks of `to_le_bits`/`to_le_bytes` (which mavros' raw `to_bits`/`to_radix`
      lowerings leave to the caller) compare against bn254's modulus. Needs a Goldilocks
      `acir_field`, or mavros replacing those paths.
- [ ] A bare HLSSA `cast WitnessOf(Field) -> Int(n)` with no `bit_range` in front is unsatisfiable
      for a value at or above `2^n`, on every field: `LowerWitnessNarrowingCast` windows an `Int`
      source only, and a `Field` source relies on the frontend emitting `bit_range(v, 0, n)` before
      the cast, which it always does.

## Layer 3 — Fixed Physical Shape (4 limb / 32 byte / 254 bit)

### `L3-felt-limbs` — The Limb-Count Constant (Representation, P4 done / signatures P5)

- [x] `vm/src/bytecode.rs` — `FELT_LIMBS` is deleted. The VM sizes frames, operands and constants
      from `F::STORAGE_CELLS`, and codegen from `FieldConfig::storage_cells()` through
      `codegen/bytecode/layout.rs::slot_cells`. `read_cells_as_field`, which reads a lookup-tape
      element of `ELEM_CELLS` kind, goes through `F::from_canonical_limbs` and asserts
      `cells <= F::CANONICAL_LIMBS`; `codegen::bytecode::lookup_elem_kind` asserts the matching
      bound where the cell count is chosen.
- [ ] `compiler/src/compiler/passes/instruction_lowering/bit_range.rs` —
      `decompose_canonical_field_bytes` assumes 32 bytes / four 64-bit limbs / a 2×128-bit modulus
      split. Its modulus _values_ are now read from `FieldConfig` (see `L4-modulus-literal`); only
      this shape is left, and it needs a per-field-width canonicalization.
- [ ] `compiler/src/compiler/util.rs` — `field_constant` builds a `[u64; 4]` because
      `FieldConfig::from_bigint` takes an `ark_ff::BigInt<4>`. The count moves with that signature,
      and the width bound it computes then becomes the per-value question it already asks.

### `L3-field-size` — 32-byte Field Size in the WASM Host (Representation, P4 — done)

- [x] `compiler/src/wasm_host.rs` — `FIELD_SIZE` is gone: `field_size::<F>()` is
      `F::STORAGE_CELLS * 8`, asserting `F` has `LLStruct::FIELD_LIMBS` cells (the runtime's
      element), and the region readers and writers go through `from_frame_cells`/`to_frame_cells`.

### `L3-opcode-width` — The Opcode Macro's 4-limb Field Operand (Representation, P4 — done)

Every generated op-set is bound to its field's type, and a field immediate is that type's storage
cells.

- [x] `opcode-gen/src/lib.rs` — the operand stride and the measurer's size are

- [x] `opcode-gen/src/lib.rs` — the getter decodes through `F::from_frame_cells`.
- [x] `opcode-gen/src/lib.rs` — the serializer encodes through `F::to_frame_cells`, and the printer
      formats the element.

### `L4-logup-challenges` — Single LogUp Challenge Assumes a Large Field (Hardcoded count, P5 — done on the VM)

The LogUp lookup argument proves the log-derivative identity `Σᵢ mᵢ/(α − tᵢ) = Σⱼ flagⱼ/(α − keyⱼ)`
(width-2 tables fold `(key, value)` into `key + β·value`). One repetition (`alpha` plus an optional
column-folding `beta`) buys `log₂ p − log₂ D` bits: about 223 on bn254 at `D = 2^30`, but about 42
on goldilocks at `D = 2^21`. Reaching a target bits-of-security needs **K independent repetitions**.

**Model (see `hlssa_to_r1cs.rs::compute_logup_soundness`).** Clearing denominators gives a nonzero
polynomial of total degree `≤ D = table_entries + num_lookups` in the challenges, so one repetition
fails with probability `≤ D/|F|` (Schwartz–Zippel) and K independent repetitions give `(D/|F|)^K`:

```
per_repetition_bits = floor(log2 p) − ceil(log2 D)      (field_bit_size() − 1)
K                   = max(1, ceil(requested_bits / per_repetition_bits)) ≤ MAX_LOGUP_REPETITIONS (16)
```

Computed with integer bit-length arithmetic (never `f64`) and rounded so `achieved_bits` is a
_lower_ bound. On bn254 `per_repetition_bits ≈ 223`, so `K = 1` for any sane request and the
constraints and witnesses are those of a single repetition. **`beta` must be replicated per
repetition** (K independent `(αₖ, βₖ)` pairs): a shared `beta` leaves the folding-collision term
un-amplified and caps security regardless of K.

A challenge that zeroes the denominator of a row whose numerator is zero (a table entry of
multiplicity zero, a lookup with a zero flag) leaves that row's inverse free, which adds at most
another `D/|F|` per repetition. Flooring `log₂ p` absorbs that factor of two on Goldilocks to within
`10⁻⁹` bits; bn254 over-reports by at most 0.41 bits per repetition, far inside its margin. Under
Fiat–Shamir these are bits per hash query: a prover grinding `2^t` transcripts gains `t` bits.

**Status — implemented.** `--logup-soundness=<bits>` (default 128) sizes K before sealing, and the
argument is repeated K times with independent `(αₖ, βₖ)` pairs and shared multiplicities.
`WitnessLayout::logup_repetitions` records K (0 without a table); the challenge section is
`[α₀, β₀, α₁, β₁, …]` (`β` only when a table has a value column), and the table-data and lookup-data
sections, in the witness and in the constraints, are K consecutive copies of one repetition's. The
prover draws all `challenges_size` challenges _independently_ (powers `α, α², …` are invalid for
this identity) after committing to the pre-commitment witness, and passes them in order to
`run_witgen_phase2`: challenge `i` sits at `challenges_start() + i`. The layout word is part of the
artifact's witness layout and of the VM header's constraint layouts. The LLVM and WASM paths refuse
`K > 1` (`Error::WasmLogupRepetitionsUnsupported`).

- [x] `compiler/src/compiler/codegen/hlssa_to_r1cs.rs` —
      `compute_logup_soundness`/`logup_soundness_report` + `SoundnessReport` (the formula,
      unit-tested); `driver.rs::logup_repetitions` sizes K from the program's `FieldConfig` before
      sealing, so the per-repetition bit budget follows the configured field.

## Layer 6 — Integer-Arithmetic Lowering Strategy (Algorithmic, P5)

Integer ops **spill into the field**: an n-bit integer (and usually the full product/sum of two) is
computed in **one** `Field` element and range-checked back to width, with place-value packing via
`two_pow(k)`. This holds only because bn254 (~254 bits) has headroom for every supported integer and
product. On a small field it breaks at **two** levels, which the constant-swap tags (`L4-two-pow`,
`L4-modulus-query`, `L3-width254`) understate — these need a genuinely different lowering
_strategy_, and a different constant does not help.

Let `B = floor(log2 p)` (bn254: 253; goldilocks: 63). For standard widths on goldilocks the break is
**mostly representational**:

- `u8/u16` and their products (≤ 32 bits): fit — single cell, any field.
- `u32`: operands fit, and so do bitwise natural-spread (≤ 32 bits), shl, the product and the
  division. `u32 × u32` (max `= p − 2³²`) is below `p`, and a `u32` division's `q·d + r` reaches
  exactly `p − 1`, so the single cell holds it with nothing to spare. The bound is stated against
  the modulus (`shared/limbs.rs::single_cell_division_fits_modulus`), since `2·32` bits exceeds
  `B = 63`.
- `u64 / u128 / i64`: a bare value's range `≥ p` (`2⁶⁴ − 1 > p`) ⇒ it **cannot be held injectively
  in one cell**; every recombination into one cell (`shared/limbs.rs`'s `combine_limbs_of_value`,
  signed `sign·2⁶⁴` packing) wraps. `lower_not`'s all-ones mask is **not** in that list: the
  representation splits a witnessed `u64` into limbs on such a field before the complement is
  lowered, so the mask is only ever minted at a width the cell holds.

So on goldilocks standard widths collapse to **{single-field for n ≤ 32, multi-cell for n ≥ 64}**,
operations included. `range_fits_field_injectively` (`witness_integer_arith.rs`) flips correctly on
a small field, and the FALSE-case codegen is the multi-cell representation in `WideWitnessInts`,
which takes each operation past the width its single-cell lowering holds. The single-cell u128 mul
packs `lo + cross·2ʰ ≈ 2³ʰ⁺¹` into one cell (~2¹⁹³ at the bn254 limb) and refuses through the funnel
below where that does not fit. The per-lowering list is under `L6-int-op-strategy`.

### Refusing On a Narrow Field

Every lowering whose precondition the configured field fails, with no FALSE-case lowering to fall
back on, refuses through one funnel, `compiler/src/compiler/passes/shared/unsupported.rs`, which
names the field's modulus and witness limb widths. Its call sites **are** the machine-readable half
of this register.

The call sites: `witness_bitwise`'s `lower_word_bitwise` (spread width); `witness_integer_arith`'s
`lower_unsigned_mul` (both the single-field product and the two-limb packing, the latter covering
the limb _count_ as well as the packing); `shared/limbs.rs`'s `combine_limbs_of_value` (the
recombination); `witness_field`'s `to_bits` and `to_radix`; `bit_range`'s
`lower_witness_field_bit_range` (the canonical decomposition at 128-bit halves, which Noir's
`x as uN` on a witnessed `Field` reaches); and `wide_witness_ints`' `schoolbook` (the product and
the division).

One kind of neighboring check deliberately stays out: an internal invariant no field choice can
violate (`bit_range`'s "a field `BitRange` cannot exceed a field element").

**P5 target — integers wider than the field must be _supported_; rejecting them is no end state.**
The end state is a **multi-cell representation** (Option A): an integer whose type range is `≥ p`
(`n > B`) is carried as `⌈n/h⌉` field cells end-to-end (witness layout, `Cast`, VM frame, opcode
stride, serde). The integer type-system cap (`MAX_SUPPORTED_INT_BITS` = 16384) stays
**field-independent** — a goldilocks `u128` is just a wider cell vector, exactly as bn254 already
carries a u128 value in one cell but its 256-bit _product_ across two. Paired with a **schoolbook
engine** for the FALSE branch (split operands into `h`-bit limbs, `h` derived from the modulus by
`compiler/src/compiler/passes/shared/limbs.rs`; in-field partial products; column-accumulate with a
witnessed, range-checked carry chain; keep the low result limbs).

Sequence within P5: multi-cell representation → mul engine → add/sub-carry → divmod → bitwise →
signed. **Dominant risk:** every witnessed limb/carry must be range-checked or a malicious prover
can forge the result.

Two tags, distinct from the constant-swap tags:

### `L6-int-op-strategy` — Single-Field Op Assumes the Result Span `< p` (Algorithmic, P5)

A single-field arithmetic op assumes its exact result span fits one cell (one `b.mul`/`b.add`, or a
`two_pow`-based packing). Fix = multi-limb schoolbook / carry-chain lowering in the FALSE branch.

- [x] `witness_integer_arith.rs` — `lower_signed_mul` and `lower_signed_divmod`, with
      `signed_value_from_encoded`/`encode_signed_value` (sign packing). The FALSE case is the
      **sign-magnitude** lowering in `WideWitnessInts`, which takes every signed witnessed product,
      division and remainder that `single_cell_signed_product_fits` (`shared/limbs.rs`) says one
      cell cannot hold. Each operand's magnitude is its limbs complemented by its sign bit (one
      product per limb) plus that bit through the carry chain; the unsigned schoolbook or division
      runs on the magnitudes; one constraint on the top bit holds the answer's magnitude to
      `2^(N − 1) − 1 + s` for its sign `s`; and the answer is negated by `s` the same way. The
      single-cell lowerings assert that bound, which also keeps their sign packing below the
      modulus: unlike the unsigned packing it has no two-limb escape at 128 bits.
- [x] `witness_integer_arith.rs` — `lower_signed_addsub`. The FALSE case is the **signed carry
      chain** in `WideWitnessInts`: the unsigned chain with its top carry witnessed, the sign bits
      of both operands and of the answer cut out of their top limbs, and one linear relation between
      the four. It takes every signed sum and difference past `widest_cell_sum_bits`, as the
      unsigned chain does, and the single-cell lowering asserts that bound, which also keeps its
      sign packing below the modulus.
- [x] `witness_integer_arith.rs` — `lower_unsigned_mul` (single-field product + the `2³ʰ⁺¹` u128
      fallback packing). The FALSE case is the **schoolbook product** in `WideWitnessInts`. It takes
      every unsigned witnessed product that `single_cell_product_fits` (`shared/limbs.rs`) says one
      cell cannot hold, decomposing an operand held as one element, and works column by column at
      the witness limb: each column is reduced into a range-checked limb and a witnessed,
      range-checked carry, and the partial products past the top are held to zero by one constraint
      per left limb. The reductions are planned from the operands' bounds against the modulus, as
      often as the field requires; where one partial product plus its headroom does not fit, the
      lowering refuses through the funnel above. On both configured fields that is out of reach: a
      column has `2^(B − 2h)` partial products of headroom (`2^125` on bn254, `2^31` on goldilocks).
      Every product that reaches `lower_unsigned_mul` passes `single_cell_product_fits`, directly or
      as the `q·d` that `lower_unsigned_divmod` re-emits after asserting it, so its two refusals
      cannot fire and stay as a backstop.
- [x] `witness_integer_arith.rs` — `lower_unsigned_divmod` (`q·divisor + r` in one field element).
      The FALSE case is the **division** in `WideWitnessInts`, which takes every unsigned witnessed
      division and remainder whose `q·d + r` one cell cannot hold (`single_cell_product_fits`). The
      quotient and remainder are witnessed as range-checked limbs, and `q·d + r == n` is one
      schoolbook: the remainder is added to its columns, and each column is held to the dividend's
      limb, with no range check. `r < d` is the carry chain with its top borrow forced out, which
      also refuses a zero divisor. A constant operand bounds both answers, so a limb they cannot
      reach is never witnessed. A division the plan cannot hold is refused through the funnel above,
      a signed one too, since that runs on the operands' magnitudes. What reaches the single-cell
      lowering fits the cell, and it asserts so.
- [x] `witness_bitwise.rs` — `lower_shift` (`value · 2^n` in one field element, or a division by
      `2^n`). The FALSE case is the **limb-wise shift** in `WideWitnessInts`, which takes every
      unsigned witnessed shift that `single_cell_shift_fits` (`shared/limbs.rs`) says one cell
      cannot hold: a left shift whose `2^(2·bits − 1)` passes the modulus, and a right shift whose
      division's `q·d + r` does. A known amount cuts each limb where its bits land on a limb
      boundary of the answer. Any other amount is `q·h + r`: `r` is keyed into the powers-of-two
      table the narrow shift already uses, every limb is split at `2^r` into two range-checked
      halves, and a barrel moves limbs by the bits of `q`. The split is unique because the limb rule
      keeps a limb times a power of two below `2^h` injective. A signed left shift is the unsigned
      one, and a signed right shift is the unsigned one with the sign filled in: by a known amount
      the vacated bits are the sign times a constant, and by any other the operand is complemented
      by its sign before the shift and the answer after it. What reaches `lower_shift` fits the
      cell, and it asserts so.
- [x] `witness_integer_arith.rs` — `lower_unsigned_addsub`; `witness_compare.rs` —
      `lower_unsigned_lt` for an unsigned ordering; and `witness_assert.rs` —
      `lower_unsigned_assert_lt` for an asserted one. The FALSE case is the **carry chain** in
      `WideWitnessInts`, which lowers every unsigned sum, difference, ordering and asserted ordering
      wider than `widest_cell_sum_bits` limb by limb, with a witnessed, bit-checked carry per limb
      and each limb of the answer range-checked at its width. That threshold is one bit short of
      `widest_injective_int_bits`, because the _sum_ has to fit. The chain also takes a value held
      as one element, decomposing it first, so it covers the width at which the operands fit but
      their sum does not. What reaches the three single-cell lowerings fits the cell on any field,
      and each asserts it: `lower_unsigned_addsub` and `lower_unsigned_assert_lt` themselves, and
      `lower_lt` for the ordering under either reading, since `lower_unsigned_lt` is also the signed
      path.
- [x] `witness_compare.rs` — `lower_signed_lt`, which orders the raw patterns through
      `lower_unsigned_lt` and selects the answer by the operands' sign bits. The FALSE case is the
      **carry chain** over the operands with their top bits flipped, which is offset binary and so
      orders them as signed values, at the same `widest_cell_sum_bits` as the unsigned ordering. On
      goldilocks `i63` and `i64` go there, as their difference does not fit the cell.
- [x] `witness_bitwise.rs` — `lower_integer_sext` (`value + sign·(2^to - 2^from)` in one element).
      The FALSE case is the **sign fill** in `WideWitnessInts`, which takes every witnessed target
      held as limbs and fills each limb past the source with the source's sign bit. What reaches the
      single-element lowering has a target the field carries, and it asserts so.
- [x] `witness_bitwise.rs` — `lower_word_bitwise` (spread width). The FALSE case is the **half-limb
      decomposition**: `lower_binary_bitwise` asks `spread_sum_fits_field` before taking the
      whole-width arm, so a width whose spread sum the field cannot hold falls through to it. A
      half-limb spread sum is below `2^h`, inside the `2h` bits the limb rule keeps injective, so
      the refusal states the coupling; it guards no reachable case.
- [x] `witness_bitwise.rs` — `lower_not`. The FALSE case is the **representation**, with no second
      lowering: `WideWitnessInts` runs before this pass, with only the narrowing-cast lowering
      between them, and splits a witnessed value wider than `multi_cell_int_bits` into limbs,
      complementing each at its width. That threshold **is** `widest_injective_int_bits`, so the
      all-ones mask this mints is bounded by `2^(bits(p) - 1) - 1 < p` on any field and cannot wrap
      at any width. The assert on the bound states the coupling; it guards no reachable case.

The `signed_value_from_encoded`/`encode_signed_value` sign packing carries a `FIELD-ASSUMPTION`
comment but no unchecked assumption: every lowering that reads it asserts the bound that keeps its
place values below the modulus, `widest_cell_sum_bits` for the sum and the difference and
`single_cell_signed_product_fits` for the product and the division.

Note that the funnel's condition is per-site, because `witness_limb_bits` certifies only that a limb
product is injective. A lowering that additionally scales a column by a place value asks
`two_limb_product_packing_fits`, one that spreads asks `spread_sum_fits_field`, and one that
recombines asks for the width of the value its limbs came from, which is `widest_injective_int_bits`
— all three in `shared/limbs.rs`, alongside the limb rule they each strengthen. The recombination
asks the value's width, and leaves the limbs' nominal span (`combined_limbs_fit_modulus`) aside,
because a decomposition may bound its top limb below a full one, and the nominal question would then
refuse widths that fit.

### `L6-int-representation` — Value Range `≥ p` Assumed to Fit One Cell (Representation, P5 multi-cell)

A value whose type range is `≥ p` (`n > B`), or a fixed limb layout, assumed to fit / recombine into
one cell. Fix = a **multi-cell (per-limb) representation** carrying the integer across `⌈n/h⌉` field
cells (the largest P5 sub-piece; touches witness layout, `Cast`, the VM frame, opcode stride,
serde). Wide integers are supported; no cap removes them.

- [x] `compiler/src/compiler/ssa/hlssa/type_system.rs` — `MAX_SUPPORTED_INT_BITS` stays
      field-independent (there is one int-type cap, and signedness is not a property of a type); the
      multi-cell representation carries any width `> B` on a small field. What _is_ field-derived is
      the narrow/wide dispatch threshold, `passes::shared::limbs::narrow_int_bits`: one field cell
      or one host word, whichever binds first.
- [x] `passes/shared/limbs.rs` — `combine_limbs_of_value` (recombines `⌈n/h⌉` limbs into **one**
      cell). The limb _widths_ are field-derived: `witness_limb_bits` derives `h` from the modulus,
      and every splitter and place value in the tree uses it. That alone does not prove the _result_
      fits, so the packing, spread and recombination sites each carry a separate predicate. The
      FALSE case is the **representation**: `WideWitnessInts` holds every witnessed value wider than
      `multi_cell_int_bits` as limbs, and the one caller, `lower_binary_bitwise`, asserts its width
      is at most `widest_injective_int_bits`. So the refusal of a value wider than one cell carries
      injectively cannot fire, and states the coupling.
- [x] `witness_integer_arith.rs` — `split_u128_value`'s caller `lower_unsigned_mul` reads the split
      as a pair, and `WitnessLimbs::pair` refuses a decomposition wider than two limbs, where
      truncating it would be wrong. The caller takes a 128-bit product only where
      `single_cell_product_fits` holds, which there asks `two_limb_product_packing_fits`, and that
      answers for the limb count as well as the packing; every other product goes to the schoolbook.
- [x] `witness_bitwise.rs` — the bitwise dispatch has its `⌈n/h⌉` arm. `decompose_into_spread_limbs`
      splits any width into `⌈n/(h/2)⌉` half-limbs and bounds each at the bits it carries, so no arm
      is keyed on a **type** width, and a narrower field gets more limbs, where a lowering keyed on
      the type would not suit the value. The arms above it are a single bit, which is field
      arithmetic at any width, and a whole-width spread, which asks `spread_sum_fits_field` before
      it is taken.

The `value_range_analysis.rs` interval domain is over `BigInt` and stays correct on any field — it
already produces the exact spans the FALSE-case codegen consumes (no new marker; only `field_top` /
`field_modulus` remain `L4-modulus-query`).

## Non-Issues

These are already deliberately field agnostic and should not be touched.

- `spread_u32_to_u64` / `unspread_u64_to_u32` and the limb-wise `spread` / `unspread` (`limb-arith`,
  shared by the VM and the WASM runtime) — pure u64 bit-tricks; only the `Field::from(..)` wrappers
  the VM's spread tables put around them change.
- The generic `SSA<Op, Ty, C>` layer — agnostic; bn254 enters only via the concrete
  `Constant::Field` variant.
- `mavros-opcode-gen` dispatch/`DISPATCH`/`OPCODE_NAMES` generation — the machinery itself is
  agnostic: Phase 4 has it generate one field-prefixed op-set per supported field, and a
  `HostType::Field` operand takes its width and encoding from that field's type (L3-opcode-width).
- Hash functions (poseidon/blake3/sha256) — these are compiled **Noir** replacements
  (`mavros_stdlib/replacements/*.nr`), not Rust; they arithmetize through the ordinary field ops
  above, so there is no Rust hash library to swap.
